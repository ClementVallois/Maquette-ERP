# ADR-0041 — Deterministic UUIDv7 for all identifiers, including child rows

- **Date**: 2026-08-19
- **Status**: accepted

## Context

`docs/BUILD-RULES.md` says "Ids are UUIDv7 generated in the application, so an aggregate can be
built without touching the database." Two systems break this rule:

1. **The seed** needs "same seed, same identifiers" (ADR-0022), but a UUIDv7 embeds a timestamp,
   so generating one from the wall clock produces a different id each run.
2. **Child-row ids** (`invoice_lines`, `cra_lines`, `cra_flags`, `invoice_vat_groups`) are minted
   as positional strings — `` `${parent.id}-line-${index}` `` — not UUIDv7. Reordering lines
   rewrites the identity of every line of a legally immutable document. Today nothing references a
   child id across a save (`#replaceLines` deletes and re-inserts), so the risk is bounded; it
   stops being bounded the moment anything holds a child id — a credit note on one line, an
   export, a URL.

Both needs are resolved by one mechanism: a UUIDv7 generator that accepts a fixed timestamp and a
deterministic counter instead of reading the clock and a random source.

## Decision

**All identifiers — parent rows and child rows — are UUIDv7, generated in the application.**

Two modes of operation:

- **Runtime** (repositories): `uuidv7()` with the wall clock and a random suffix. Lives in each
  module's `infrastructure/` layer, which may import `node:crypto`. The domain never calls it: an
  aggregate receives its id, and child ids are generated by the repository before persisting.
- **Seed** (deterministic): `uuidv7Deterministic(timestamp, counter)` with a frozen timestamp and
  a monotonic counter. Produces the same output on every run.

Both functions live in a new `scripts/lib/` directory, not in `@erp/platform`: the generator needs
`node:crypto` (runtime mode) or takes a counter (seed mode), and `@erp/platform` imports not even
a Node builtin (ADR-0033, BUILD-RULES § Boundary). The repositories import from `scripts/lib/` at
seed time, and from their own local copy at runtime — or, once `apps/api/` exists (Phase 5), from
the composition root.

The generator is hand-written rather than imported: Node 24's `crypto.randomUUID()` is UUIDv4 only,
and the RFC 9562 layout is 22 lines of bit-packing, which is simpler than evaluating a library
against the dependency grid.

## Rejected option

**Keep positional strings for child rows** — `${parent.id}-line-${index}`. It works today because
`#replaceLines` deletes and re-inserts, but the id of a line on a legally immutable invoice would
change if the lines were reordered, and any reference to that id (a credit note on one line, a
webhook payload, an export row) would be broken by a reorder that the domain allows. A UUIDv7
generated before the first persist is stable across reorders.

## Reconsideration threshold

The generator is used to produce a sort-order guarantee in a context where sort order matters (an
event stream, a distributed trace). At that point the monotonic suffix must be clock-synchronized
across processes, and the hand-written generator is replaced by one that provides that guarantee.

## Consequences

- Every id in the database is a valid UUIDv7. No positional string, no v4.
- Child-row identity is stable: reordering lines does not rewrite ids.
- The seed produces identical ids on every run, and those ids are valid UUIDv7 with a frozen
  timestamp prefix.
- Repositories gain an `id` parameter on child-row persistence methods, or generate the id before
  the INSERT rather than inline. The `#replaceLines` / `#replaceVatGroups` pattern changes: child
  ids are generated once and reused on re-save, not regenerated from the index.
